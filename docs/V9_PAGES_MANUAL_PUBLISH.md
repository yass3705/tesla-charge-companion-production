# V9 Pages: automatic validation and manual publication

The global V9 preview workflow continues to run on matching pull requests, pushes to `main`, and its daily schedule. These events resolve current Stable and Data Lab source commits, build the preview, and run the existing source, tariff, OCPI, congestion, Electroverse, runtime and browser checks. They do **not** configure GitHub Pages, upload a Pages artifact, or run the Pages deployment job.

Publication requires a deliberate `workflow_dispatch` with the Boolean `publish=true` (default `false`). The same condition guards `Configure Pages`, `Upload V9 global preview`, and the `deploy` job. A manual run with `publish=false` is a validation run. To publish, obtain the separate deployment authorization, choose the intended ref and source pins in GitHub Actions, set **Publish the validated V9 preview to GitHub Pages** to true, and review the successful build and browser tests before treating the resulting Pages deployment as published. The workflow's `github-pages` environment remains the deployment gate. A passing PR, push, scheduled run, commit, or Data Lab report is not deployment evidence.

The legacy iPhone Pages workflow is manual-only and also requires `publish=true`; its old push trigger has been removed. Both Pages publication paths share the `v9-global-pages-publish` concurrency group with cancellation disabled. Automatic global validations use a separate group per ref and may cancel only another validation for that ref. Neither can cancel a Pages publication.

**Remaining branch-specific exposure before claiming a repository-wide guarantee:** the remote branch `v9/interface-foundation-frozen-snapshot` still has its own older copy of `deploy-v9-iphone-preview.yml` with a `push` trigger for edits to that workflow file. The `github-pages` environment currently permits both `main` and that legacy branch. Merging this change into `main` will not rewrite the workflow on the legacy branch, and its older concurrency group does not serialize with the new one. Before declaring that *no Production push can publish Pages*, separately retire the legacy branch's Pages deployment permission or update/remove that branch's workflow under an authorized change. This local commit does not change GitHub environment settings or the legacy branch.

Other Production publication paths remain separate: `cloudflare-deploy.yml` is manual, with `promote_current` defaulting to false; snapshot/runtime release workflows publish GitHub Releases on their own workflow-file push or a manual event, not on normal V9 runtime changes; the historic r8 builder is manual-only. The read-only source freshness audit, pinned development dry run, Data Lab collections, and Updater Test updates do not depend on the Pages steps. This change does not alter their triggers, pins, data, or validation logic. An intentional future edit to a release workflow file can still start its release workflow, so review those path filters separately before such an edit.

The static gate test `python3 -m unittest tests/test_v9_pages_publish_gate.py -v` checks both Pages workflows, manual defaults, each publication condition, the validation events, retained tests, and concurrency groups. When Production PR #36 contributes `tests/v9-pricing-time-zone.test.mjs`, the test also requires its command in the global validation workflow. Before merging that PR, review the combined workflow diff to ensure its time-zone test and these publication guards both remain.
